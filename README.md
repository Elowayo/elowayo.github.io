# elowayo.github.io

Public site for **Elowa** — the introduction page plus the legal documents
(Privacy Policy, Terms of Service), in English and (once published) Korean.
Static HTML generated by a small Python script and deployed to GitHub Pages
by GitHub Actions.

```
site.json                    which languages are published
tools/build.py               builds _site/ from content/ (no dependencies)
tools/md2html.py             the tiny markdown converter it uses
assets/css/style.css         Blush & Mulberry palette from the app's docs/BRAND.md
assets/img/logo.svg          the "Profile & Glow" mark
content/                     legal markdown, copied in at build time (not committed)
.github/workflows/deploy.yml build + deploy to Pages
```

## URLs

| Page | English | Korean |
|---|---|---|
| Home | `/index.html` | `/ko/index.html` |
| Privacy Policy | `/privacy.html` | `/ko/privacy.html` |
| Terms of Service | `/terms.html` | `/ko/terms.html` |

English stays at the root because shipped apps link there. Every page carries
`<html lang>`, `hreflang` alternates, and a language dropdown (English /
한국어) in the header that links to the same page in the other language. The
dropdown is a `<details>` menu of plain links, so it works without JavaScript. There is no automatic redirect by browser
language. The usage-measurement section has the id `5a-usage-measurement` in
both languages (the app links `terms.html#5a-usage-measurement`); other
heading ids come from the heading text.

## Where the documents come from

The source of truth is the private app repo, `Elowayo/Elowa`, on `main`:

| App repo file | Copied to |
|---|---|
| `Terms of Service.md` | `content/terms-of-service.md` |
| `Privacy Policy.md` | `content/privacy-policy.md` |
| `Terms of Service.ko.md` | `content/terms-of-service.ko.md` |
| `Privacy Policy.ko.md` | `content/privacy-policy.ko.md` |

`.github/workflows/deploy.yml` checks out those four files, copies them into
`content/`, runs `python3 tools/build.py`, and deploys `_site/` to Pages. It
runs when:

- something is pushed to `main` here,
- it is started by hand (Actions → Deploy site → Run workflow),
- the app repo sends a `legal-docs-updated` `repository_dispatch`. The app
  repo's `.github/workflows/legal-docs-dispatch.yml` does that whenever one of
  the four files changes on its `main`.

Generated HTML and the copied markdown are not committed: the workflow
rebuilds them on every deploy, so a committed copy could only go stale.

`tools/build.py` removes text that must not appear on a live page but stays in
the markdown: HTML comments (the Korean drafts open with internal drafting
notes in one), the Korean "초안 — 게시 전" draft notice, the "starting draft / not reviewed by a licensed attorney"
footnote, and the aside in Terms §13 about BC arbitration language.

## Publishing a language

`site.json` lists the published languages:

```json
{ "published_languages": ["en"] }
```

A language not listed is not built at all, and the switcher does not offer
it; with only one language the switcher and `hreflang` links are left out.
`en` must always stay listed.

The Korean documents are drafts (their header says 게시 금지) until legal
review and the vendor contacts are done (Elowa-0dm.9). To publish Korean
after that:

1. Finish the review and merge the final `.ko.md` files to the app's `main`.
   The draft notice (`> **초안 — 게시 전.** …`) and the leading `<!-- … -->`
   notes are stripped by `tools/build.py`, so they never reach the site.
2. Here, change `site.json` to `["en", "ko"]` and merge to `main`. The push
   deploys the site with `/ko/` pages and the switcher.

## Build and preview locally

```bash
cp "../Elowa/Terms of Service.md" content/terms-of-service.md
cp "../Elowa/Privacy Policy.md" content/privacy-policy.md
cp "../Elowa/Terms of Service.ko.md" content/terms-of-service.ko.md
cp "../Elowa/Privacy Policy.ko.md" content/privacy-policy.ko.md
python3 tools/build.py
python3 -m http.server 4173 --directory _site
```

To see Korean locally without publishing it, set `site.json` to
`["en", "ko"]`, build, and put it back before committing.

## One-time setup (manual)

These are repository settings and secrets; the workflows cannot set them up.
Do them in this order, before merging the PR that removed the committed HTML
(until Pages builds from Actions, the old branch build would serve a site with
no pages):

1. **Token.** Create a fine-grained personal access token
   (GitHub → Settings → Developer settings → Fine-grained tokens), resource
   owner **Elowayo**, with access to only these repositories:
   - `Elowayo/Elowa` — **Contents: Read-only** (to read the documents),
   - `Elowayo/elowayo.github.io` — **Contents: Read and write** (needed to
     send `repository_dispatch`).

   Metadata: Read-only is added automatically. If the organization requires
   approval for fine-grained tokens, approve it under the org's settings.
   Note the expiry date; both workflows fail when it lapses.
2. **Secrets.** Add the token as an Actions secret (Settings → Secrets and
   variables → Actions → New repository secret):
   - in `Elowayo/elowayo.github.io` as `APP_REPO_TOKEN`,
   - in `Elowayo/Elowa` as `SITE_DISPATCH_TOKEN`.

   (Two separate tokens with one permission each also work, and are tidier.)
3. **Pages source.** In `Elowayo/elowayo.github.io`, Settings → Pages →
   Build and deployment → Source: **GitHub Actions**.
4. Merge the PR, or run the workflow by hand (Actions → Deploy site → Run
   workflow), and check https://elowayo.github.io/terms.html.
